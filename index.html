Exercise 1 — Introductory (5 pts)

Core Concepts
  1. Git Process Flow (no commands)
    • Branching model: Create feature branches from main/develop. Keep scope focused.
    • Work & commit: Commit frequently with meaningful messages; follow standards & tests.
    • Sync & integrate: Rebase/pull often to reduce drift; keep branch fresh.
    • Review: Open PR → peer review (style, tests, security). Address feedback.
    • CI: Automated build & tests must stay green.
    • Merge: Squash/merge when approved; tidy branch.
    • Release: Tag releases; use hotfix branches for urgent fixes.
  2. Portability (NFR)

    Ability to run on multiple platforms/configurations (OS, browsers, hardware). Verifiable via explicit targets, e.g., “supports Windows/Linux/macOS; Chrome/Firefox/Safari” validated by compatibility tests.

  3. CEO wants item mid-Sprint (Scrum)

    Developers safeguard the Sprint Goal. No mid-sprint scope change. Product Owner re-prioritizes backlog; schedule next sprint or cancel current sprint if goal is obsolete.

  4. XP Principles
    • TDD: Red → Green → Refactor. Guides design & ensures correctness.
    • Collective Ownership: Any dev edits any code. Encourages shared quality.
    • Sustainable Pace: 40h/week rhythm; prevents burnout & supports refactoring.

Exercise 2 — Processes & Models (4 pts)

Model Picks
  1. Why Waterfall for multi-company projects?

    Provides contract-friendly phases, exhaustive documentation, stable interfaces, predictable hand-offs, and smoother compliance across vendors.

  2. Choose models & justify
    a) Mobile Fitness + Social (startup)

    Model: Agile (Scrum + XP)
    Why: Rapid feedback, fluid scope, small iterations, user-centric learning.

    b) Hospital Management

    Model: RUP or Plan-driven with heavy validation
    Why: Regulatory constraints, safety-critical qualities, risk-driven milestones, disciplined documentation.

Exercise 3 — Requirements Analysis (5 pts)

Classification

Extract user/system requirements + classify FR/NFR

Functional Requirements (FR)
  • Autonomous navigation through aisles (1–3 m wide).
  • Locate & retrieve products from shelves (2–3 m high).
  • Handle objects ≤ 10 kg with ±2 cm precision.
  • Real-time sync with WMS (inventory, errors).
  • Return to docking at 20% battery.
  • Manual control via remote/app (Emergency Stop, navigation, pickup/release, seamless mode switch, error notifications).
Non-Functional Requirements (NFR)
  • Battery life ≥ 8h on single charge.
  • Intuitive remote/app controls.
  • Low-latency real-time comms with WMS.
  • Immediate emergency stop; safe obstacle handling.
  • Maintain ±2 cm precision (quality/performance).

Tip: Numbers (widths, heights, weights, precision, battery) are easy marks—cite them!

1) Programming vs Software Engineering

Mindset Shift
  • Program = code that “works once”.
  • Software = program + docs + config + data; must be maintainable, adaptable, team-friendly.
  • Ad-hoc vs SE: “Just make it run” ↔ “Deliver value that lasts.”
Hello World is easy; the hard part is sustainable value, change-readiness, and shared understanding via design & abstraction.

5) Requirements Engineering (RE)

Get it right

What & Why

  • RE = systematic discovery, documentation, and management of requirements & constraints.
  • Goal: produce requirements that are complete, consistent, relevant, verifiable.
  • Poor requirements drive failures; embrace change with discipline.

Types

Functional (FR)

What the system shall do (services, behaviors).

Non-Functional (NFR)

How it should be (quality, constraints): performance, security, usability, reliability, scalability, portability, etc.

Write NFRs as verifiable statements, not vague wishes (e.g., “90% of actions < 2s”).

Process (4 Activities)

  1. Elicitation: Plan, identify stakeholders, use interviews, scenarios, prototyping, observation, JAD, surveys, docs.
  2. Analysis: Spot missing/overlapping/ambiguous/unrealistic requirements; negotiate & resolve conflicts.
  3. Documentation: Craft SRS (IEEE 830/Volere). Qualities: correct, complete, unambiguous, verifiable, modifiable, traceable.
  4. Validation: Review with stakeholders for completeness, consistency, conformance, technical accuracy; iterate drafts.
Principles: value orientation, engage stakeholders early/often, write clearly (SMART), capture context, ensure traceability & versioning, adapt to process model, never ignore NFRs, define Acceptance Criteria, iterate Problem→Requirement→Solution, use visuals, prioritize (MoSCoW).

6) User Stories • AC • DoD • Acceptance Tests

Scrum toolkit

Stories (3Cs & INVEST)

  • Format: “As a <user>, I want <action> so that <value>”.
  • 3Cs: Card, Conversation, Confirmation (AC/tests).
  • INVEST: Independent, Negotiable, Valuable, Estimable, Small, Testable.
  • NFRs in Scrum: Bake into AC, technical stories, or team DoD.

Acceptance Criteria (per story)

  • Define “right thing” for the story; write before/during refinement.
  • Include functional + relevant NFRs.

Definition of Done (global)

  • Quality checklist for any backlog item.
  • Evolves with the team (code review, tests ≥ 80%, perf/security checks, docs, staging pass).

Acceptance Tests (prove AC)

  • Executable (often BDD given/when/then); verifies AC.

7) UML — Use Cases & Class Diagrams

Visual grammar

Use-Case

  • Elements: System, Actors (primary/secondary), Use Cases, Relationships (association, generalization, <<include>>, <<extend>>).
  • Best practices: clear verbs/nouns, consistent abstraction, factor shared behavior, package when numerous.

Class Diagram — Essentials

  • Class (name | attributes | operations); visibility: + - # ~; /derived, static.
  • Relationships:
    • Association with multiplicities/direction.
    • Association Class adds attributes to a link.
    • Aggregation = shared whole–part.
    • Generalization = inheritance (hollow arrow to parent).
    • Dependency = dashed “uses”.
  • From requirements: extract nouns → candidate classes/attributes; trim UI verbs; remove redundancy.
